# Wiki 输出契约

> 本契约定义模型生成 Wiki 候选时必须遵守的格式规范。模型生成后，CLI 必须执行确定性后校验；违反契约时不得产生候选。

## 一、页面结构

1. 页面主标题使用 `#`，全文只允许出现一次。
2. 章节使用 `##`，必须带连续中文编号（一、二、三……）。
3. 小节使用 `###`，仅用于章节内部的次级分组。
4. 章节之间使用 `---` 分隔。
5. 页面顶部必须有未审核免责声明，未审核内容不得使用“已确认事实”等确认性措辞。

## 二、章节顺序

以下核心章节必须存在且保持顺序。可选的“支撑论断”和“审核状态”放在“来源”之后；“构建信息”始终是最后一个章节。

| 顺序 | 章节名 | 内容 |
|---|---|---|
| 1 | 一句话说明 | 用一句话说明主题，用于判断页面是否相关 |
| 2 | 整体概述 | 给出核心结论、范围和阅读骨架 |
| 3 | 事实陈述 | 呈现来源直接支持的事实，不逐条显示详细定位 |
| 4 | 综合推断 | 基于事实的分析解释，明确推断属性 |
| 5 | 已知限制与待确认事项 | 未核验内容、冲突和缺失证据 |
| 6 | 来源 | 简洁的人类可读来源列表 |
| 可选 | 支撑论断 | 指向机器可审计的 Claim 或附属清单 |
| 可选 | 审核状态 | 人工审核待办项 |
| 最后 | 构建信息 | Source、范围、模型、哈希等溯源信息 |

禁止使用“三十秒概览”作为章节名。

## 三、信息呈现

1. Markdown 正文保持可读，不在每条事实或推断末尾追加文件、块 ID 和行号。
2. 详细溯源保留在 Claim 元数据、候选 JSON 或支撑论断清单中。
3. 多项指标、统计分布、清单矩阵、方案比较和状态对照优先使用 GitHub 风格 Markdown 表格。
4. 代码流程、架构、组件关系和系统交互在来源充分时优先使用 GitHub 可渲染的 Mermaid。
5. 缺少明确关系证据时不得为了绘图补造节点、调用或依赖。
6. 普通叙述使用短段落或无序列表，避免深层嵌套。

## 四、表格契约

1. 表格至少包含两列。
2. 表头之后必须有分隔行，例如 `|---|---|`。
3. 表头、分隔行和数据行的列数必须一致。
4. 单条事实若集中包含三组或以上数值，应改为表格，而不是密集列表项。

## 五、Mermaid 契约

1. 使用 ` ```mermaid ` 围栏并以 ` ``` ` 闭合。
2. 第一条有效语句必须是 GitHub 支持的图类型声明，例如 `flowchart`、`sequenceDiagram`、`classDiagram`、`stateDiagram-v2`、`erDiagram` 或 `gitGraph`。
3. 图只表达来源支持的结构或关系。
4. CLI 提供基础语法校验；复杂 Mermaid 的最终 GitHub 渲染仍需在人工审核中确认。

## 六、标题语言

1. 标题禁止不必要的中英混合，例如“支撑 Claim 清单”。
2. 英文仅允许专业术语、组件名和专有名词，例如 Karmada、Queue、CI、CLI、API、Git、OIDC。
3. 论断类型使用中文：事实、推断、建议、决策。

## 七、后校验

模型生成后必须运行：

```bash
python3 -m knowledge_core.cli --workspace <workspace> --output-dir output wiki validate --file <document.md>
```

`wiki build` 已自动执行相同校验。独立命令用于校验人工渲染文件或历史文档。

所有正式生成文档必须进入仓库根级 `output/`。实验候选、调试响应和日常工作记录不得写入或提交到该目录。
